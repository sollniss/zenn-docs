# キーノート：Towards Go 1.∞（Austin Clements）

初日のキーノートはGoチームのテックリードであるAustin Clementsさんによる「Towards Go 1.∞」でした。タイトルの通り、Goが今後何十年も生き残るために何をしていくかという話です。

内容は大きく二つの軸がありました。

一つ目は言語・プラットフォームの進化です。AIによる業界の激変の中でも、Goはシンプルさ・信頼性・効率・長寿命という基本原則を軸にして進化していくという話でした。具体的には以下のような機能が挙げられました。

- ジェネリックメソッド（generic methods）
- `json/v2`
- SIMDサポート

興味深かったのは「人間の開発者とコーディングエージェントの両方に向けたプラットフォーム」という考え方です。ツールチェーンも人間とエージェントの両方が使うことを前提に設計していくとのことで、GoをAIシステム構築の基盤言語にしていく意志を感じました。

二つ目はGoプロジェクト自体のガバナンスの話です。GoogleとGoコントリビューターコミュニティの間の壁を取り払うために、より開かれたガバナンスモデルに移行していくと発表されました。コントリビューターラダーを整備して、実績のあるメンテナーにより大きな権限を与え、プロポーザルプロセスもよりコミュニティ主導で透明性の高いものにしていくそうです。「Goが我々（Googleのチーム）より長生きするように」という言い回しが印象的でした。

# Loosening the Reins: Go Generics Get More Flexible（Naoki Kuroda / IBM）

Go 1.18でジェネリクスを覚えてから、その後の変化を追っていない人向けのキャッチアップトークです。構文はほぼ変わっていないものの、水面下では制限が着実に緩和されてきたことが紹介されました。

- ジェネリック型エイリアス（generic type aliases）
- 仕様からの「コア型（core types）」の削除
- 再帰的な型制約のサポート

これらのGo 1.26までの変更によって、型安全な順序付きコンテナ、fluent builder、ジェネリックなグラフ走査など、以前は書けなかった・書きにくかったパターンが実用レベルになったという内容でした。Goチームがなぜこれらを少しずつ段階的に入れてきたのか、というトレードオフの解説もあり、実際のコード例中心で分かりやすかったです。

# Go and {A}I Save the Bees（Cassie Coyle / Diagrid）

個人的に今日一番ほっこりしたトークです。ミツバチの個体数減少が問題になっている中、養蜂の巣箱管理を分散システムの問題として捉えて、Goで養蜂インテリジェンスプラットフォームを作ってしまったという話でした。

# Building Self-Optimizing Worker Pools in Go（Casey Manus / Bayer Crop Science）

午前のコーヒーブレイクを挟んで、ワーカープールを「自己最適化」させる話です。Goの並行処理プリミティブで素朴なワーカープールを作るのは簡単ですが、そこから機械工学と生物学の概念を借りてどこまで行けるか、という内容でした。

流れとしては、

1. リモートシステムからデータを取得するワーカープールを作る
2. 処理件数、レイテンシ、エラー率、CPU・メモリ使用率などのメトリクスを公開する
3. PID制御（比例・積分・微分）でワーカー数、バッチサイズ、バックオフを動的に調整する
4. さらに進化的アルゴリズムでメトリクスに応じて設定を自動チューニングする

PID制御は車のクルーズコントロールやエアコンのサーモスタットに使われているものです。ソフトウェアのチューニングに制御工学を持ち込む発想が面白く、会場でも反応が良かったです。

# Lightning Talks

昼食後は7分以内のライトニングトークが7本連続で行われました。どれも粒ぞろいだったので全部紹介します。

**The Life, Death, and Rebirth of testing/quick（Akshay Shah / Antithesis）**
標準ライブラリにひっそり存在するプロパティベーステストのパッケージ`testing/quick`の話です。「17個目以降の名前を無視してしまう`LongestName`関数」という絶妙なバグを例に、通常のテーブルテストでは見逃すバグをプロパティベーステストが一発で見つける様子を見せてくれました。ただし`testing/quick`が報告する反例は読めないUnicodeの塊で、シュリンキング（最小の反例への縮小）がない、入力データを制御できない、一様分布で境界値を狙ってくれない、といった限界があるためパッケージは凍結されたそうです。「Rebirth（転生）」パートでは、その反省を活かした新しいプロパティベーステストライブラリ[Hegel](https://hegel.dev)が紹介され、`__proto__`や`NaN`、`1e100`、Zalgoテキストのような「意地の悪い」最小反例を返してくれるデモが披露されました。[スライドはこちら](https://docs.google.com/presentation/d/1Inr515gt994uwjEYqjNxc7GKnlSfg2-cR9utT1MuN_g/edit)。

**Three Simple Data Structures Built on Slices（Simon Law / Tailscale）**
スライスだけでスタック、キュー、min-heapによる優先度付きキューをその場で書けるようになろうという話です。「小さな依存をimportする代わりに、少しタイピングしよう」というメッセージがGoらしくて好きでした。[スライドはこちら](https://docs.google.com/presentation/d/e/2PACX-1vRqnhc-Ad0PtI53U5gCGA8cXvmV_cNT4gRFZtMHu5pB2y5gi4SWH3XhqcpwDWWgzYxFXATDd6mHXEsa/pub)。

**Unix Pipes are Better Than Agents（Derick Schaefer）**
LLMにツールやエージェントフレームワークを与えるのではなく、CLIツール自身が自分の使い方（コンテキスト、意図、例、パイプラインパターン）を説明できるようにして、決定的で再現可能なUnixパイプラインに処理を寄せるアプローチです。FRED（経済データ）を探索するGo製CLI「Reserve」を題材にしていました。トークンを洞察に使う、という視点が新鮮でした。

**h.Sum(data) Does Not Hash Data（Ruslan Kadyrov / Mercari）**
Goの`hash.Hash`インターフェースの`Sum`メソッドは「データをハッシュする」のではなく「これまで書き込んだ内容のハッシュに引数を追記して返す」という、誰もが一度は誤解するAPIの話です。`sha256.Sum256`とストリーミングハッシュの違いなど、低レベルAPIの小さな誤解が本番で静かに壊れるコードを生む例として面白かったです。

# (Sync)testing Concurrent Code with Confidence（Alexander Baygeldin / Evil Martians）

並行処理のテストは「ハック・フレーキー・遅い」のトリレンマになりがちですが、`testing/synctest`パッケージによってイディオマティックで高速かつ安定したテストが書けるようになりました。

synctestの中核は「無限に速いコンピュータ」のシミュレーションです。テストを「バブル」の中で実行し、バブル内のすべてのゴルーチンが恒久的にブロック（durably blocked）した瞬間を検知することで、`time.Sleep`のような時間頼みの不安定な待ち方を排除します。`time.Sleep`、チャネル操作、`sync.WaitGroup`、すべてのcaseでブロックしているselect文などは「恒久的なブロック」として認識される一方で、システムコールやI/O、そしてパフォーマンス上の理由で計装されていない`Mutex.Lock`は認識されない、という制約が丁寧に解説されました。ネットワークには`net.Pipe`、mutexにはビルドタグで差し替えるラッパーといった回避策も紹介されています。

バッチ処理するグリーターサービスを題材にしたリファクタリングのデモでは、トランスポート（チャネル通信）・実行（ゴルーチン協調）・ビジネスロジックをレイヤーとして分離すると自然とsynctestフレンドリーになることが示され、「テストが書きにくいのはツールではなく設計の問題であることが多い」「synctestの制約は良い並行処理設計を教えてくれる」という主張が印象に残りました。[スライドはこちら](https://speakerdeck.com/baygeldin/sync-testing-concurrent-code-with-confidence)。

# Unlocking Real-World Go Mutex Usage Patterns by Writing a Mutex Linter（Vladimir Dementyev / Evil Martians）

AnyCableやTestProfの作者として知られるVladimirさんが、`Unlock()`忘れのバグに苦しめられた経験から「自分のmutexの使い方は間違っているのか？」を突き詰めた話です。発端は本番で実際に起きたバグで、クリティカルセクションの途中に`if s.IsClosed() { return nil, nil }`のような早期returnがあり、ロックを握ったまま抜けてしまうというものでした。これを機に、長らく放置されていたgnieto/mulintを蘇らせる形で、ロックの取得・解放の不均衡を検出するリンター[mulint](https://github.com/palkan/mulint)を作り上げました。

面白かったのは、リンターを実世界のコードベースにかけて浮かび上がってきたmutex使用パターンの分類です。I/Oや重い処理の間だけロックを手放す「no-lockウィンドウ」、クロージャやコールバックに解放責任を渡す「ハンドオフ」、アサーションやシャーディング、可観測性を足したカスタムmutexの「ラッパー」、他のゴルーチンを飢えさせないために一度譲って取り直す「協調的ロック」、そして状態依存のロック契約をコメントの規約で表現するパターンの5つです。検出精度は自身のAnyCableでは100%（例のバグもちゃんと検出）でしたが、whatsmeowでは87%、nats-serverでは32%と、コードベースの流儀によって大きくばらつき、条件付きロックや文書化されていない状態前提が偽陽性の温床になるという静的解析の難しさも率直に語られました。それでも解析の過程で複数の実際のデッドロックを発見できたそうです。go/analysisベースのリンターを書く際の知見も多く、静的解析に興味がある人には刺さる内容でした。[スライドはこちら](https://speakerdeck.com/palkan/gophercon-2026-unlocking-real-world-go-mutex-usage-patterns-by-writing-a-mutex-linter)。

# Pure-Go Tree-sitter: From Zero to Self-Hosted Infra with Oracles and Bench Gates（Oscar Villavicencio / M31 Labs）

エディタのシンタックスハイライトやコードインテリジェンスを支えるTree-sitterは、Goから使うと必ずCGoが付いてきます。クロスコンパイルやWASMターゲット、シングルスタティックバイナリと相性が悪いこの問題を、[Pure-GoのTree-sitterランタイム](https://github.com/odvcencio/gotreesitter)を作ることで解決した話です。

規模がすごくて、レジストリには206の文法が同梱され、すべてがスモークテストを通過しています。しかもそのうち119の文法が必要とする外部スキャナーは手書きのGoで実装されているそうです。パースだけでなく、クエリ、ハイライト、タグ、埋め込み言語のパース、そして次のパースに引き継がれる構造的な書き換えまで、「パーサーとプロダクトの間のレイヤー」を丸ごと提供するのがコンセプトです。

面白いのは実装の多くがAI支援で書かれたことを公言しつつ、本題は「LLMの書いたコードをどう信用するか」だったことです。合言葉は「AIが提案し、エビデンスが決める（AI proposed; evidence decided）」で、次のようなハーネスが紹介されました。

- C実装を「オラクル」として、同じソースと文法を両方に通して結果を構造的に比較するパリティチェック
- 失敗を最小の再現ケース（witness）に縮小してからAIに修正させ、そのwitnessを恒久的にテストスイートに残す
- 一度通った品質基準を二度と下げられなくする「ラチェット」
- 見せかけの高速化を検出するベンチマークゲート

過去の看板ベンチマークが「木の実体化をスキップしたパスを計測していた」ことを監査で発見し、公の場で数字を撤回したそうです。現在の公表値はフルパースでC実装の約4.8倍の所要時間（コンパクトルートで約4.0倍）と正直な数字で、その代わり1バイト編集後のインクリメンタルパースは約2マイクロ秒、編集なしの再パースは10ナノ秒未満・ゼロアロケーションという数字が示されました。

そして一番のポイントは「このスライド自体がデモ」だったことです。スクリーンに映っているものはMarkdown++で書かれたスライドをGoTreeSitterの文法でパースし、GoSXコンポーネントにコンパイルしてGoアプリケーションとして動かしているとのことでした。画面上の構文木はクリックで折りたためて、それもWASMにコンパイルされたGoで動いています。最後には「観測可能な契約を決める→独立した検証者（witness）を作る→AIに境界の中で自由に探索させる→失敗を縮小する→証明をラチェットで固定する→実プロダクトでドッグフードする」という、大規模プロジェクトにAIを使うためのプレイブックが提示されました。昨日までのワークショップでもローカルLLM関連が多かったですが、本会議でもAIとの付き合い方が大きなテーマになっていると感じます。[スライド（ソースごと公開されています）はこちら](https://github.com/M31-Labs/gosx-slides/tree/main/examples/gophercon2026)。
