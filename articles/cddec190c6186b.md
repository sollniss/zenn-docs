# The Go Cryptography State of the Union（Filippo Valsorda / Geomys）

Goの暗号ライブラリのメンテナーであるFilippoさんによる、毎年恒例の「今年のGo暗号事情」です。暗号の世界はいま、Filippoさんのキャリアの中でも類を見ない速さで変化しているそうですが、アプリケーション側の破壊を最小限に抑えながら安全性を保つ、というGoらしいスタンスが貫かれていました。

トピックは盛りだくさんでした。

- 新しいML-DSAパッケージとそのテスト手法
- ポスト量子暗号への移行準備
- 新しいHPKEパッケージ
- 乱数とエントロピーの話

ポスト量子暗号のパートの「量子コンピュータは普通のコンピュータより速いのではなく、普通のコンピュータにできないことができる」という説明が個人的に分かりやすかったです。締めは恒例の「来年の予告」で、Merkle Tree Certificates（とupki）、TLSプロファイル、チャンク暗号化に対応した新しいAEAD API、そして`crypto/passkey`が挙げられました。「あまり深く考えなくても安全に暗号化できるAPI」を目指しているとのことで、来年のこのトークも楽しみです。

# What slog Left on the Table（Dylan Bourque / CoreWeave）

Go 1.21で標準ライブラリ入りした`log/slog`は基本を押さえている一方で、大規模な実運用では痛みになるギャップが残っている、という話です。`slog.Handler`インターフェースの上に作った二つの拡張が紹介されました。

一つ目は`testing.T`と統合するカスタムハンドラーで、ログをテストの出力にルーティングすることで、成功したテストではログのノイズを抑えつつ、失敗したテストでは本番相当のフルログを表示してくれます。ハンドラーの実装からハマりどころのエッジケースまでの解説もありました。最初の実装は`t.Log()`でレコードを書いていたため、`t.Log()`が注入する呼び出し元のファイル名・行番号によって「全ログ行が`test_handler.go:42`で始まる」状態になってしまったそうで、これはGo 1.25で追加された`t.Output()`（テストの出力バッファへ直接書ける`io.Writer`）で解決。ただし今度は、テスト終了後まで生き残ったゴルーチンがログを書くとpanicする（以前はtesting内部のデータ競合だったのが、今は明示的なpanicになっている）という罠があり、ハンドラーが`t.Cleanup()`でテストの終了を検知して、終了後のレコードはコールスタック付きの警告としてstderrに逃がすようにしたとのこと。クラッシュを避けるだけでなく、ゴルーチンのライフタイムバグを「うるさく」教えてくれる仕組みになっているのが上手いところです。

二つ目はコンポーネント単位で動的にログレベルを変えられる仕組みです。導入の「午前3時の悲劇」に聞き覚えのある人は多いはず。オンコール中にサービスが変なエラーを吐き始めたのでERRORをDEBUGにして再起動したら、毎秒5万行のログの雪崩に襲われ、しかも再起動で悪い状態が消えて肝心のエラーが再現しなくなる、というやつです。`slog.LevelVar`で動的なレベル変更自体はできるものの、一度ハンドラーに渡すと後からLoggerやHandler経由で取り出せず、システムのどの部分のレベルなのかという意味づけもないため、大きなアプリケーションでは運用が破綻します。解決策は`server.api`のようなドット区切りのコンポーネント名と`LevelVar`を対応づけるレジストリで、`server.api`をDEBUGにするとそのサブツリーだけに継承され、兄弟の`server.database`には影響しない、という階層的な制御ができます。JavaやPythonが組み込みで持っている「名前付き・階層ロガー」をslogの部品で組み立てた形です。性能面も抜かりなく、レベルの解決はハンドラー構築時に済ませて読み取りは`LevelVar`への直接アクセスにすることで、素の`slog.TextHandler`と比べて時間+1.5%・アロケーション増なし（コンポーネント名を属性として付けた場合のみ+15%）というベンチマーク結果が示されました。再起動なし・パフォーマンスペナルティなしで特定のサブシステムだけDEBUGにできるというもので、「DEBUGを有効にしたらログの雪崩で肝心のログが埋もれた」経験のある人には刺さる内容でした。

この二つの拡張は[slogext](https://github.com/dylan-bourque/slogext)として公開されています。全体で2,000行程度なのでコピペでも持っていけるそうです。テストハンドラーの方は[標準ライブラリへのproposal](https://github.com/golang/go/issues/80138)も出ているので、いずれ`slog`本体に入るかもしれません。[スライドはこちら](https://github.com/gophercon/2026-talks/tree/main/DylanBourque-WhatslogLeftOnTheTable)。

# Parsing Protobuf as Fast as Possible（Sunny Young de la Sota / Buf Technologies）

Buf社の[hyperpb](https://github.com/bufbuild/hyperpb-go)という、あらゆる高速化テクニックを注ぎ込んだGo向けProtobufパーサーの話です。テーブル駆動パーシングというパーサーのパラダイムと、その上に積んだhyperpb独自の工夫、そしてコンパイラ・パーサーVM・レイアウト最適化といった全体アーキテクチャが解説されました。

話の組み立てが上手くて、素朴な`Unmarshal`を書くと「フィールドごとのcaseを持つ巨大なswitchをループで回す」形になりますが、これはまさにインタープリタの構造そのもの（「インタープリタとは、ループの中の巨大なswitchである」）で、だからこそHotSpotやPython、Rubyのインタープリタで培われた高速化テクニックがProtobufパーサーにも適用できる、という流れで進みました。hyperpbのVMは「computed goto」スタイルのループで、`vm = thunks[opcode](vm)`のようにオペコードごとのthunk関数を辿っていく作りです。全体は「ディスクリプタコンパイラ → VM設定+thunks → VM実行+プロファイリング」の三段構成で、実行時のプロファイルがコンパイラにフィードバックされるPGOのループまで組み込まれています。手描き風のスライドも可愛くて、Advanced枠だけあって内容は濃く、パフォーマンスチューニングの引き出しが増えるトークでした。

# From Go to Factorio: What Games Can Teach Us About Compilers（Simon Li / Meta）

Goコンパイラがプログラムを変換していく途中経過という「普段誰も見ない隠れたレイヤー」を、ゲームのFactorioの工場として可視化して遊んでしまおうという話です。「The factory must grow.」の一文で会場のFactorioプレイヤーは全員ニヤリとしていました。

このために作られた[gofactos](https://github.com/siutsin/gofactos)というツールは公開されていて、サポートされたサブセットのGo関数を本当にFactorio 2.0のブループリントに変換できます。コンパイラ内部のSSAは外から使えないため、`golang.org/x/tools/go/ssa`の公開SSAパッケージでGoコードをSSA形式に落とし、それをFactorioのサーキットネットワーク（信号とコンビネーター）に配置していく作りです。「回路」という制約から来る設計判断がいちいち面白くて、

- サーキットネットワークでは「信号なし」と「0」が区別できないため、boolは`1`/`-1`で表現する
- 回路にpanicはないので、ゼロ除算はpanicせず0を返す
- 再帰しない関数呼び出しはすべて呼び出し側に展開（インライン化）され、再帰はルート関数の直接再帰のみ、スタックは13フレームまで
- ループと再帰は1Hzのクロック（`--fast`で4Hz）で駆動され、ブループリントにSTART/RESETスイッチが付いてくる

といった具合です。デモの再帰フィボナッチは実際に工場として動くアニメーションになっていました。コンパイラの中間表現をここまで楽しく見せる発想はなかなかないと思います。

# Sandboxing DuckDB with io/fs（Achille Roussel / Firetiger）

Cライブラリを組み込んだGoプログラムには「Cライブラリが自前のI/Oスタックを持ち込んでくる」という隠れた罠があります。Cライブラリ側はGoの認証情報もTLS設定もリクエストトレーシングもリトライロジックも知らないので、同じバイナリの中に二つのI/Oシステムが並走してしまうという問題提起から始まりました。

題材は組み込みデータベースのDuckDBです。httpfsやawsといった拡張はC++から直接ネットワークI/Oを行うため、Goでラップするとオブザーバビリティもクレデンシャル管理も失われてしまいます。解決策として、Go 1.16で入った`io/fs`インターフェースとDuckDBの仮想ファイルシステムAPIを小さなC++拡張でブリッジし、ライブラリのI/OをすべてGoランタイム経由に戻すパターンが紹介されました。「Goの`fs.FS`をDuckDBの仮想ファイルシステムとしてマウントできないか？」という問いの立て方がきれいです。このパターンは他のCライブラリにも応用でき、DuckDB向けにはこれを実装したOSSライブラリも公開されているそうです。

まとめのテイクアウェイには、`io/fs`でC側のI/Oを捕まえる話に加えて「動的リンクと決定的ビルドの両立」「Cのコールスタックを越えた`context`の伝播」も並んでいて、DuckDBに限らずCGoでCライブラリを組み込むアプリケーション全般に効く話でした。

# Receipts from the Go Linker: Auditing the Cost of Dependencies（Mikayla Toffler / Datadog）

「すべてのimport文はトランザクションなのに、私たちはレシートを確認しない」という掴みが秀逸なトークでした。go.modからコンパイル後のシンボルまで依存を追いかけて、Goリンカーが実際に何をバイナリに取り込むのか、デッドコード除去（DCE）がどこで効いてどこで失敗するのかを解説してくれました。

DCEが無効化される条件が具体的で勉強になりました。「①バイナリのどこかで問題のあるreflectメソッドが呼ばれている」かつ「②到達可能なコードのどこかで型がインターフェースに代入されている」の二つが揃うと、リンカーは安全側に倒してメソッドを刈り取れなくなります。`reflect.Value.Method`と`reflect.Type.Method`は常にDCEを無効化し、`MethodByName`は引数がコンパイル時定数でない場合のみ無効化する、という細かい挙動まで整理されていて、しかもこの条件は自分のコードだけでなく推移的依存の中で満たされても発動します。対策としてはビルドタグでimportごと外す方法と、依存を使うシンボルを別パッケージに切り出して必要なときだけimportする方法が紹介されました。

最後には、ライセンス・コミットの新しさ・メンテナーの応答性などで依存を見極めるヒューリスティクス、`go tool nm`・`go mod why`・whydeadcode・goda・go-size-analyzerといった調査ツール、そしてビルドタグ・モジュール分割・CIチェック・「a little copying」・vendoringといった対策までが一枚にまとまった「依存問題への処方箋」が提示されました。Goのことわざ「a little copying is better than a little dependency」と「車輪の再発明をするな」の間の緊張関係に正面から触れていたのも良かったです。ライブラリメンテナーにもプロダクトエンジニアにも役立つ、依存を評価するためのツールキットが持ち帰れる内容でした。

**AI is a Power-up, Not a Player（Seth Lumnah / Capital One）**
大きな組織で共有Goライブラリをメンテナンスする立場から、「ボトルネックはコードではなく注意力（attention）」という洞察を軸に、スタイルガイドをAIに参照させて定型作業を任せるエージェントスキル（Markdownファイル）の実例を紹介してくれました。前提になるのは「標準化されていないものは自動化できない」という原則で、lint設定・スタイルガイド・プロポーザルテンプレートといった決めごとをプレーンテキストとしてリポジトリに置いておかないと、AIは「もっともらしいノイズ」を生成するだけになってしまいます。実際に使っているスキルとしては、プロポーザルを5つの観点（APIの明快さ、Goのベストプラクティス、ライブラリの規約、互換性、依存への影響）でレビューする`/review-proposal`、PRをdiffではなく実際のコードとしてworktreeにチェックアウトしてレビューする`/review-pr`、週次・月次のコミュニティ向けアップデートを生成するスキルが挙げられました。ポイントは、冒頭の説明文だけでなく議論のスレッド全体を読ませること（プロポーザルは20コメントの議論を経ると別物になっているので）、そしてAIの出力は必ずメンテナーが編集してから投稿するという規律です。成果として「作るのが大変すぎて止まっていた月次アップデートが毎月出るようになり、週次まで始まった」「リポジトリ史上最高のアウトプットの月と重なった」ことが紹介され、「スキルは雑魚敵を掃除してくれるが、設計判断とコミュニティの信頼というボス戦は自分で戦う」という締めが、タイトルの「AIはパワーアップアイテムであってプレイヤーではない」に繋がっていました。ちなみにスライド自体もMarkdownベースのターミナル用プレゼンツールpresentermで作られていて、まさに「Markdown all the way down」でした。[スライドはこちら](https://github.com/sedalu/presentations/blob/main/gophercon/2026/slides.pdf)。

# Uber-Scale Changes: Managing Millions of Lines of Go（Sung Whang / Uber）

UberではGoが最も使われている言語で、Goモノレポは2億行・80万Goファイル超、そこから1,000以上のサービスがデプロイされ、月間約1万コミット・2,000人以上のコミッターが今も書き続けているそうです。そんなコードベースで数万ファイルにまたがる「Uberスケールの変更」をどう実施するかという話で、AST変換ツールとAIによる自動化の仕組みが紹介されました。

道のりが面白くて、gopatchのような変換ツールから始まり、それを大規模に走らせるオーケストレーターとして「Shepherd」を構築、静的解析と決定的なツール群で数十件の大規模変更を回せるようになったところで「人間に良いツールはエージェントにも良い」となり、エージェントが同じツール群を使ってタスクを進めるようになったそうです。今ではShepherdの上に「Fawkes」を構築して、モノレポ全体でメンテナンスループが自動で回る「自己改善するコードベース」になっているとのこと。「静的解析ツールは、エージェントがより少ないトークンでより速く問題を発見する助けになる」という指摘は、AIエージェントと既存ツーリングの関係を考える上で示唆的でした。

Go本体のアップグレードの話も生々しかったです。Hyrumの法則の通り、Goのリリースごとに社内では数百パッケージ規模で何かが壊れ、その多くは「誰かが暗黙の挙動に依存していた」ケース（正真正銘のGoのバグもあり、その場合はissueとパッチを送る）だそうで、「今この瞬間もチームの誰かがGo 1.27に備えて何かを直している」と笑いを取っていました。規模の桁が違いすぎて笑ってしまいましたが、大規模リファクタリングの考え方自体はどの組織でも参考になると思います。

# Detect, Trace, Fix: Bringing AI-Powered Taint Analysis to gosec（Ravi Sastry Kadali / General Motors）

セキュリティ解析ツールのgosecに、AI対応のテイント解析エンジンを持ち込む話です。信頼できないデータがアプリケーション全体をどう流れるかを追跡することで、SQLインジェクション、コマンドインジェクション、パストラバーサル、SSRF、XSSなどを正確に検出します。SSAとコールグラフに基づく解析がGoにおけるデータフロー追跡を実用的にし、偽陽性を大きく減らすこと、そして同じアーキテクチャがAIによる自動修正の基盤になることが解説されました。

モデル自体は驚くほどシンプルで、SOURCE（信頼できない入力：リクエスト、環境変数、CLI引数）・SANITIZER（無害化処理）・SINK（危険な操作：クエリ、ファイルオープン、コマンド）の三つのリストと、「汚染された値から作られた値も汚染される」というたった一つの伝播ルールだけ。バグは「sourceからの汚染が、sanitizerに止められることなくsinkに到達すること」と定義されます。ルールはv2.23で最初の6つ（G701〜G706：SQLインジェクション、コマンドインジェクション、パストラバーサル、SSRF、XSS、ログインジェクション）が出荷され、その後コミュニティから5つ（SMTPインジェクション、テンプレートインジェクション、安全でないデシリアライゼーション、オープンリダイレクト、無制限のフォームパース）が追加されて、同じエンジンの上に11ルールが載っているそうです。

テイクアウェイの「SSAとCHA（コールグラフ解析）は`x/tools`にある。importを二つ書けば、Goのデータフロー解析はもう特別なものではない」「構造こそがAIの修正を安全にする。source-to-sinkのパスがなければ、それはCVE番号の付いたオートコンプリートに過ぎない」という言葉が特に刺さりました。「検出する」から「追跡し、理解し、修正する」へというGoセキュリティツーリングの方向性を感じるトークでした。

# Automation Tools for Large-Scale Go Code Transformations（Ian Alexander / Google, Go Team）

Goチーム自身も大規模なコード変換に取り組んでいます。goコマンドのモジュールローダーやGoコンパイラの内部構造のリファクタリングを題材に、複雑なマージコンフリクトの解消や、時間のかかる大規模変更（LSC）をプログラマティックな変換で乗り切るテクニックが紹介されました。

整理として、LSCを「空間的LSC」（巨大な変更を独立したシャードに分割して並列に処理・レビューする「ダイヤモンドパターン」。爆発半径を最小化する）と「時間的LSC」（ベースブランチが動き続ける中で、長期にわたるパッチ列やコミットチェーンを絶え間ないリベースで管理する「チェーンパターン」）の二軸で捉えていたのが分かりやすかったです。リリース前のコードフリーズが解けた瞬間に全員が狭いドアへ殺到してマージコンフリクトが爆発する現象を「Simpsonsのバイ菌」と呼んでいたのも笑いました。

ツールは二本立てで、Goプログラムを変換するエンジンの「rf」と、特殊な形式のコミットメッセージにシェルスクリプトを埋め込んでおき、そのスクリプトからコミットを再生成する「git-generate」が紹介されました。「コンフリクトは手で解消するのではなく、再生成で解決する」というのが肝です。題材のモジュールローダーのリファクタリングでは、ローダーに影響する大量のエクスポートされたグローバル変数を`State`構造体に集約し、トップレベルの関数呼び出しに注入していく過程が示されました。最後の5つの教訓——「Goは設計からしてマシン編集可能」「自動化はドキュメンテーション」「コンフリクトは再生成で解決」「空間と時間の両方で考える」「小さく始めて速くスケール」——はそのまま持ち帰れます。Uberのトークと合わせて聴くと、大規模コード変換が一つの分野として確立しつつあるのを感じます。

# Chasing the Moon: Engineering a High-Performance Lua VM in Pure Go（Salah Mahmud / Palliser Analytics）

NeovimやRedis、Nginxなどで使われている組み込みスクリプト言語Luaを、Pure Goで高速に実装した話です。C実装のPUC LuaをGoに組み込むとCGoのビルドの複雑さと呼び出しオーバーヘッドが付いてきますが、既存のPure Go実装は2〜3倍遅くメモリも食う、というのが従来の状況でした。新しいレジスタベースのVMはCGoフリーのままPUC Lua比の30〜50%以内の性能を達成したそうです。

# Building a Durable Agent & MCP Execution Engine in Go（Samantha Kendziora / Diagrid）

AIエージェントのフレームワークのほとんどはdurable（耐久的）ではなく、ツール呼び出しの途中でプロセスが落ちると実行もコンテキストも失われてゼロからやり直しになります。さらにMCPではelicitation（ユーザーへの入力要求）やsampling（LLM補完のトリガー）でツール呼び出しが数分単位で中断・再開されうるため、単純なリトライループではモデル化できない、という問題設定です。

解決策として、決定的リプレイ、チェックポイントベースの再開、Virtual ActorパターンとGoのプリミティブによる耐久性エンジン、そして透過的な組み込みMCP durabilityワーカーという構成要素が解説されました。昨日のミツバチのトークに続いてDiagridの方による発表で、ワークフローエンジン技術の応用範囲の広さを感じました。
