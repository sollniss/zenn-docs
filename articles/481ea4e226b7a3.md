メソッドチェーン形式のビルダーはGoでよく使われるパターンです。オブジェクトをステップごとに構築し、各メソッドがビルダー自身を返すことでチェーンが可能になります：

```go
client.NewRequest().
    WithURL("https://api.example.com/users").
    WithMethod("GET").
    WithHeader("Accept", "application/json").
    Do()
```

これは単一パッケージで書く分には簡単です。しかし、ビルダーを*拡張可能*にしたい、つまり、異なるパッケージのメソッドを同じチェーンで利用可能にし、どのパッケージのメソッドであってもコンポジット型全体を返す、となると、驚くほど難しくなります。

この記事では、きれいな解決策にたどり着くまでの設計上の判断、行き詰まり、ベンチマークを順を追って解説します。

## なぜ単純なビルダーはパッケージをまたぐと壊れるのか

まず思いつく実装：ビルダーメソッドを持つベースのリクエスト型と、メソッドを追加する拡張パッケージです。

```go
package httpbuilder

type Request struct {
    Method  string
    URL     string
    Headers map[string]string
}

func (r *Request) WithMethod(m string) *Request    { r.Method = m; return r }
func (r *Request) WithURL(u string) *Request       { r.URL = u; return r }
func (r *Request) WithHeader(k, v string) *Request { r.Headers[k] = v; return r }
```

```go
package authext // 認証ヘルパーを追加

func WithBearer(r *httpbuilder.Request, token string) *httpbuilder.Request {
    return r.WithHeader("Authorization", "Bearer "+token)
}
```

パッケージをまたぐたびにチェーンを分断しなければならず、メソッドを合成できません：

```go
r := httpbuilder.New()
r.WithURL("https://api.example.com").WithMethod("GET")
authext.WithBearer(r, "my-token")   // チェーンが切れる、合成できない
r.WithHeader("X-Request-ID", "123") // ビルダーに戻る
```

自然な対策は `*Request` をコンポジット型に埋め込み、各パッケージが独自のミックスイン型にメソッドを追加することです：

```go
type MyRequest struct {
    *httpbuilder.Request
    *authext.AuthExt
}
```

しかし、これでは何も解決しません。`r.URL("...")` が返すのは `*httpbuilder.Request` であり、`*MyRequest` ではありません。ベースのメソッドが呼ばれた瞬間にチェーンが切れます。チェーンを維持するには、すべてのメソッドが*最も外側のコンポジット*を返す必要があります。ベース型にはそれが何なのか知る術がありません。

## 自己参照ジェネリクスという解決策

重要な洞察：`Base` がコンポジットへのバックポインタを保持していれば、メソッドはそれを返せます：

```go
type Base[Self any] struct {
    Method  string
    URL     string
    Headers map[string]string
    Self    *Self
}

func (b *Base[Self]) WithMethod(m string) *Self { b.Method = m; return b.Self }
func (b *Base[Self]) WithURL(u string) *Self    { b.URL = u; return b.Self }
```

`Self = MyRequest` であれば、`Base.WithURL` は `*MyRequest` を返します。拡張ミックスインも同じ形を取ります：

```go
type AuthExt[Self any] struct{ Parent *Self }

func (a *AuthExt[Self]) WithBearer(token string) *Self { /* ... */ }
```

コンポジットがそれらを一つにまとめます：

```go
type MyRequest struct {
    *httpbuilder.Base[MyRequest]
    *authext.AuthExt[MyRequest]
}
```

すべてのパッケージのすべてのメソッドが `*MyRequest` を返します。チェーンが切れることはありません。

## nilポインタの罠

パターンは正しく見えますが、最初のテストで`panic`が起きます：

```go
func TestRequest(t *testing.T) {
    r := MyRequest{
        Base: &httpbuilder.Base[MyRequest]{},
        AuthExt: &authext.AuthExt[MyRequest]{},
    }
    r.WithURL("https://api.example.com").WithMethod("GET") // panic: nil pointer dereference
}
```

`WithURL` は `b.Self` を返しますが、これは `*MyRequest` のゼロ値、つまりnilポインタです。チェーンの次の呼び出しがそれを逆参照してパニックになります。

`Self` は一度も設定されていません。Goには構築後のフックがないため、バックポインタは明示的に設定する必要があります：

```go
r := MyRequest{
    Base: &httpbuilder.Base[MyRequest]{},
    AuthExt: &authext.AuthExt[MyRequest]{},
}
r.Self = &r  // バックポインタを設定

r.WithURL("https://api.example.com").WithMethod("GET") // 動作する
```

`Base.Self` についてはこれで解決します。しかし `AuthExt` もメソッドから返すためのバックポインタが必要です。ミックスインが1つだけであれば、ジェネリックなコンストラクタがプロモートされたセッターを使って自動的に処理できます：

```go
type Mixin[Self any] interface {
    setSelf(*Self)
}

func (b *Base[Self]) setSelf(s *Self) { b.Self = s }

func New[T any, PT interface {
    *T
    Mixin[T]
}](s PT) PT {
    s.setSelf(s)
    return s
}

// 使い方：
r := New(&MyRequest{Base: &Base[MyRequest]{}})
```

`setSelf` の呼び出しが埋め込まれた `*Base` を通じてプロモートされ、バックポインタが正しく設定されます。これはミックスインが1つだけであれば動作します。

## 兄弟ミックスインの問題

2つ目のミックスインを加えると、また問題が発生します：

```go
type MyRequest struct {
    *httpbuilder.Base[MyRequest]
    *authext.AuthExt[MyRequest]
    *bodyext.BodyExt[MyRequest]
}
```

`New` は `s.setSelf(s)` を呼び出し、これが `(*Base).setSelf` にプロモートされて `Base.Self` を設定します。しかし `AuthExt.Parent` と `BodyExt.Parent` はゼロ値、つまりnilのコンポジットのままです。どちらかのミックスインのメソッドが最初に呼ばれた瞬間にパニックになります。

問題は構造的なものです：複数の兄弟ミックスインのバックポインタを繋げるには、*コンポジットのフィールドを列挙*する必要があります。Goのジェネリクスにはそのためのメカニズムがありません。プロモートされた単一の `setSelf` は1つのフィールドにしかアクセスできず、兄弟には展開できません。実行時に構造体のフィールドを列挙できるのはリフレクションだけです。

## 3つの設計選択

リフレクションに頼る前に、このパターンが取り得る異なる形を検討する価値があります。パフォーマンス特性が大きく異なるためです。

### 設計A：値渡し型、ゲッター/セッターインターフェース

設計Aでは、これまでの `Parent *Self`（ポインタによるバックリファレンス）とは異なり、各ミックスインはコンポジット全体をインターフェースとして保持し（`Parent Self`）、そのインターフェースを通じてベースのデータにアクセスします：

```go
type Mixin interface {
    GetData() Request
    SetData(Request)
}

type Base[Self Mixin] struct {
    Data Request
    Self Self
}

type AuthExt[Self Mixin] struct{ Parent Self }

func (a *AuthExt[Self]) WithBearer(token string) Self {
    // ベースのデータにはインターフェースを通じてしかアクセスできない
    req := a.Parent.GetData()
    req.Headers["Authorization"] = "Bearer " + token
    a.Parent.SetData(req)
    return a.Parent
}
```

`GetData`/`SetData` はジェネリックスを通じてディスパッチされます。これは実質的にインターフェース呼び出しのオーバーヘッドであり、データアクセスのたびに発生します。`Parent Self` を保持することは、メソッドが返るたびにコンポジット全体（複数の埋め込みポインタを持つ構造体）をコピーすることでもあります。

### 設計B：共有 `*Base` ポインタ、散在するアロケーション

各ミックスインはコンポジットではなく、_同じ_ `*Base` ポインタを埋め込みます：

```go
type AuthExt[Self any] struct{ *Base[Self] }

func (a *AuthExt[Self]) WithBearer(token string) Self {
    // Dataとselfは埋め込まれた*Baseから直接プロモートされる
    a.Data.Headers["Authorization"] = "Bearer " + token
    return a.Self
}
```

データアクセスが直接になります（`a.Data`、ディスパッチなし）。しかしコンポジットは依然として複数の埋め込みポインタを持つ構造体で、構築時にミックスインの数+1ヒープアロケーションが発生し、メモリ上に散在します。

### 設計C：値埋め込みコンポジット、単一アロケーション

コンポジットにすべてを値で埋め込み、各ミックスイン内で `*Base` をポインタ埋め込みします：

```go
type MyRequest struct {
    httpbuilder.Base[MyRequest]   // 値埋め込み
    authext.AuthExt[MyRequest]    // 値埋め込み
    bodyext.BodyExt[MyRequest]    // 値埋め込み
}
```

`new(MyRequest)` は単一のアロケーションです。各ミックスインは同じ構造体内を指す `*Base[MyRequest]` を保持します。直接フィールドアクセス、単一アロケーション、キャッシュフレンドリーなレイアウトが実現します。

## リフレクションによるコンストラクタ

エクスポートされたフィールドにより、単一のジェネリックコンストラクタが型ごとのボイラープレートなしにあらゆるコンポジット型を自動的に繋げることができます：

```go
func New[T any]() *T {
    p := new(T)
    v := reflect.ValueOf(p).Elem()

    baseType    := reflect.TypeFor[Base[T]]()
    basePtrType := reflect.TypeFor[*Base[T]]()

    // ステップ1：コンポジット内の値埋め込みBase[T]フィールドを探す。
    var baseField reflect.Value
    for i := range v.NumField() {
        if f := v.Field(i); f.Type() == baseType {
            baseField = f
            break
        }
    }

    // ステップ2：Base.Selfをコンポジットに設定する。
    baseField.FieldByName("Self").Set(reflect.ValueOf(p))
    basePtr := baseField.Addr()

    // ステップ3：各ミックスインの埋め込み*Base[T]を共有Baseに向ける。
    for i := range v.NumField() {
        f := v.Field(i)
        if f.Type() == baseType {
            continue
        }
        if f.Kind() == reflect.Struct {
            inner := f.FieldByName("Base")
            if inner.IsValid() && inner.Type() == basePtrType {
                inner.Set(basePtr)
            }
        }
    }

    return p
}
// BenchmarkNew 189.4 ns/op, 32 B/op, 1 allocs/op
```

この走査は設計が保証する2つの不変条件に依存しています：

- コンポジットは値埋め込みの `Base[T]` フィールドをちょうど1つ持つ。
- 連携が必要な各ミックスインは `*Base[T]` を埋め込む（フィールド名 `Base` と型 `*Base[T]` で識別）。

どちらも構築時に検証可能です。コンポジットの形が正しくなければ、`New` は壊れた値を黙って返すのではなく、明確な `panic` を起こします。

特定のコンポジット型がホットループ内で構築される場合、`NewManual` がゼロボイラープレートのコストを示します（単純な代入のみで、リフレクションなし）：

```go
func NewManual() *MyRequest {
    r := &MyRequest{}
    r.Self = r
    r.AuthExt.Base  = &r.Base
    r.BodyExt.Base = &r.Base
    return r
}
// BenchmarkNewManual: 24 ns/op, 32 B/op, 1 alloc/op
```

189 nsのリフレクションオーバーヘッドは、ビルダーが長命であれば素早く償却されます。タイトなループ内で短命なビルダーを構築する場合は、`NewManual` がいつでも使えるローカルな最適化として機能します。デメリットとしては、`NewManual` は `MyRequest` を定義する側が併せて定義する必要があります。リフレクションを使った `New` であれば、 `Base` と同じパッケージに存在するため、ボイラープレートが不要でAPIがスッキリします。

## 実世界の例

3つのパッケージにわたる完全なパターン：コアHTTPリクエストビルダー、認証拡張、ボディー拡張。

### パッケージ `httpbuilder`

```go
package httpbuilder

import "reflect"

// Baseは共有リクエスト状態とコンポジットへのバックポインタを持ちます。
// Selfはパッケージをまたいだミックスインがそれを返せるようにエクスポートされています。
type Base[Self any] struct {
    Body    []byte
    Method  string
    URL     string
    Headers map[string]string
    Self   *Self
}

func (b *Base[Self]) WithMethod(m string) *Self {
    b.Method = m
    return b.Self
}

func (b *Base[Self]) WithURL(u string) *Self {
    b.URL = u
    return b.Self
}

func (b *Base[Self]) WithHeader(k, v string) *Self {
    if b.Headers == nil {
        b.Headers = make(map[string]string)
    }
    b.Headers[k] = v
    return b.Self
}

// NewはBase[T]を値で埋め込み、*Base[T]を埋め込むミックスインを持つ
// あらゆるコンポジットを繋ぎます。型ごとのコンストラクタは不要です。
func New[T any]() *T {
    p := new(T)
    v := reflect.ValueOf(p).Elem()

    baseType    := reflect.TypeFor[Base[T]]()
    basePtrType := reflect.TypeFor[*Base[T]]()

    var baseField reflect.Value
    for i := range v.NumField() {
        if f := v.Field(i); f.Type() == baseType {
            baseField = f
            break
        }
    }

    baseField.FieldByName("Self").Set(reflect.ValueOf(p))
    basePtr := baseField.Addr()

    for i := range v.NumField() {
        f := v.Field(i)
        if f.Type() == baseType {
            continue
        }
        if f.Kind() == reflect.Struct {
            if inner := f.FieldByName("Base"); inner.IsValid() && inner.Type() == basePtrType {
                inner.Set(basePtr)
            }
        }
    }

    return p
}
```

### パッケージ `authext`

```go
package authext

import "github.com/example/httpbuilder"

// AuthExtはあらゆるリクエストコンポジットに認証ヘルパーを追加します。
// *httpbuilder.Base[Self]を埋め込んでいます。エクスポートされた埋め込みフィールド名
// "Base"がリフレクションコンストラクタの検索対象です。
type AuthExt[Self any] struct {
    *httpbuilder.Base[Self]
}

func (a *AuthExt[Self]) WithBearer(token string) *Self {
    return a.WithHeader("Authorization", "Bearer "+token)
}

func (a *AuthExt[Self]) WithAPIKey(key string) *Self {
    return a.WithHeader("X-API-Key", key)
}
```

`WithHeader` は埋め込まれた `*Base[Self]` からプロモートされているため、`a.WithHeader(...)` は `(*Base).WithHeader` を直接呼び出して `a.Self` を返します。ゲッター/セッターの間接参照もパッケージをまたいだVisibilityの問題もありません。

### パッケージ `bodyext`

```go
package bodyext

import (
    "encoding/json"
    "net/url"
    "github.com/example/httpbuilder"
)

type BodyExt[Self any] struct {
    *httpbuilder.Base[Self]
}

// WithBodyは*Selfではなくて中間型を返します。
// この時点で、Bearer()やWithURL()などはチェーンから利用できなくなります。
func (m *BodyExt[Self]) WithBody() *BodyBuilder[Self] {
    if m.Headers == nil {
        m.Headers = make(map[string]string)
    }
    return &BodyBuilder[Self]{base: m.Base}
}

// BodyBuilderはボディフォーマットの選択を1つに絞り込みます。
// 各メソッドは*Selfを返してメインチェーンに戻ります。
type BodyBuilder[Self any] struct {
    base *httpbuilder.Base[Self]
}

func (b *BodyBuilder[Self]) JSON(v any) *Self {
    data, _ := json.Marshal(v)
    b.base.Body = data
    b.base.Headers["Content-Type"] = "application/json"
    return b.base.Self
}

func (b *BodyBuilder[Self]) Form(values url.Values) *Self {
    b.base.Body = []byte(values.Encode())
    b.base.Headers["Content-Type"] = "application/x-www-form-urlencoded"
    return b.base.Self
}
```

### 拡張を合成する

ユーザーは必要な拡張を値埋め込みすることでコンポジットを定義します：

```go
package myapp

import (
    "github.com/example/httpbuilder"
    "github.com/example/authext"
    "github.com/example/bodyext"
)

type Request struct {
    httpbuilder.Base[Request]
    authext.AuthExt[Request]
    bodyext.BodyExt[Request]
}
```

`httpbuilder.New[Request]()` は1つの `Request` 構造体をアロケートし、`Self` と両ミックスインの `*Base` ポインタを配線して、すぐに使える状態で返します。ボイラープレートも型ごとのコンストラクタも不要です：

```go
r := httpbuilder.New[Request]()

r.WithURL("https://api.example.com/users").
    WithMethod("GET").
    WithBearer("my-secret-token").
    WithBody().JSON(map[string]string{"name": "Alice"}).
    WithAPIKey("my-key")
```

すべてのパッケージのすべてのメソッドが `*Request` を返します。どれだけ多くのパッケージを合成しても、チェーンが切れることはありません。

後から `Request` に新しい拡張（たとえば `tracingext.TracingExt[Request]`）を追加する場合は、構造体にフィールドを追加するだけです。次回の呼び出しから `New[Request]()` が自動的にそれを検出して紐付けます。

```go
type Request struct {
    httpbuilder.Base[Request]
    authext.AuthExt[Request]
    bodyext.BodyExt[Request]
    tracingext.TracingExt[Request] // ← ここに追加するだけでメソッドが使えるようになります。
}
```

## まとめ

このパターンの最終的な形：

| 関心事                                           | 解決策                                                                                                  |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| メソッドがコンポジットを返す                     | `Base[Self any]` が `Self *Self` を保持する                                                             |
| パッケージをまたいだミックスインのデータアクセス | ミックスインが `*Base[Self]` を埋め込む（すべての `Base` フィールド/メソッドがプロモートされる）        |
| コンポジットごとに1アロケーション                | コンポジットが `Base` と全ミックスインを値埋め込みする                                                  |
| ボイラープレートをゼロに                         | ジェネリックな `New[T any]()` がリフレクションで `Self` と全ミックスインの `*Base` フィールドを紐付ける |
| パフォーマンスクリティカルなホットパス           | 型ごとの `NewManual()`（単純な代入、24 ns、1アロケーション）                                            |

これを成立させる2つの制約：

1. コンポジットは `Base[T]` をちょうど1回、値で埋め込む必要がある。
2. 各ミックスインは `*Base[T]` を埋め込む必要がある（名前付きフィールドではなく、エクスポートされた埋め込みフィールド名がリフレクションの走査で識別される）。

リフレクションのオーバーヘッド（約190 ns）は構築時のコストのみです。一度構築されると、設計Cのメソッドチェーンは手書きのポインタ追跡と同等の速度になります。6メソッドのチェーンで約6 ns、アロケーションなしです。これはゲッター/セッター設計の15 nsと比較して2.5倍高速です。
