# 「いつの間にか動かなくなったサンプルコード」問題

おそらくどんなプロジェクトでも、READMEや設計書、コード内のコメントにサンプルコードを書いているのではないかと思います。書いたときは完璧に意図通りになりますが、プロジェクトが変わっていく中で、いつの間にかサンプルコードがもう存在しない関数や型を使ったり、コンパイルしなくなったりしませんか？最初からタイプミスなどにより、間違っていた可能性も十分にあると思います。実際にLSPが参照できるわけではないので、チェックのしようがないかな、と思いきや、方法がありました。

最も簡単な対策は、コードサンプルを全て`Example`関数に入れることではありますが、関数に絞られることによって、本来不要なコードやセットアップ用のコードも`Example`関数に入れないと動かない場合も多いので必ずしもきれいに完結したサンプルになるとは限らないと思います。また、見つけやすさも公開されていない場合にはかなり悪いと思います。公開されているコードであれば`go.dev`には表示されますが⋯⋯それくらいです。

特にAI時代にmarkdownファイルがかなり主役になってきましたので、mdファイルに記載されているコードも実際のコードから拾えないかを調べてみました。

1つ見つけたのは`embedmd`でした。GoogleのエンジニアがGoで書いたツールで、すでに10年以上の歴史があるそうです。

https://github.com/campoy/embedmd

フォーマットは以下の通りです：
```markdown
[embedmd]:# (pathOrURL language /start regexp/ /end regexp/)
```

始まりと終わりのRegexしか指定できず、途中からスキップやバラバラのインデントはサポートされていないようです。自分が求めていたのと少し違ったので、作ろうと思いました。

# mdファイルのコードを同期する mdsync

https://github.com/sollniss/mdsync

使い方は以下の通りです：
~~~
<!-- MDSYNC:<lang> from:<source-file> [attributes] -->
```lang
```
~~~

ほとんどのMarkdownレンダラーはHTMLコメントを表示しないので、HTMLコメントのマーカーにしています。

利用可能なアトリビュートは以下です。

|  | 用例 | 説明 |
|---|---|---|
| `from:` | `from:main.go` | ソースファイル（必須） |
| `start-at:` | `start-at:"func Foo"` | 指定のRegexからサンプルが始まる |
| `start-offset:` | `start-offset:-1` | 始まりを N 行ずらす（マイナスも可能） |
| `end-at:` | `end-at:"^}"` | 指定のRegexでサンプルが終わる |
| `end-offset:` | `end-offset:2` | 終わりを N 行ずらす（マイナスも可能） |
| `skip-match:` | `skip-match:"//nolint"` | 指定のRegexにマッチした行をスキップする |
| `skip-after:` | `skip-after:"^import" count:3` | 指定のRegexにマッチしたN行後からスキップする |
| `skip-between:` | `skip-between:"// BEGIN":"// END"` | 2つの指定のRegexの間をスキップする |
| `tab-size:` | `tab-size:4` | サンプルにあるタブをスペースに変換する（デフォルト値：`2`） |
| `region:` | `region:myFunc` | `#region`/`#endregion`コメントの間をサンプルにする |

ほとんどのサンプルコードでスキップ機能が不要のため、現時点で最も使っているのは`region`です。

```go
// #region handleRequest
func handleRequest(w http.ResponseWriter, r *http.Request) {
    // ...
}
// #endregion
```

サンプルコードが普通のGoファイルにあることで、LSP、リンター、コンパイラーのチェックが通常通りに行われるので、Readmeなどを手動で管理しなくて良くなりました。

## 実装でこだわった点

##### コードサンプル以外のmdファイルを処理しない

`bufio.SplitFunc`を使って、特にmdファイルの改行（CRLF／LF）が変わらないように処理しています。

##### Markdownはパースしない

単純なステートマシンを作って以下の4つのステートを実装しています。
- テキスト
- MDSYNCコメント
- マルチラインMDSYNCコメントの中
- コードサンプルの中

##### MDSYNCコメントをパースするためのちゃんとしたレクサー

Regexで下手にやるより、最初からレクサーを考えて、パースエラー時のエラーメッセージもきれいになるように実装しています。

##### Regexのフォールバック

万が一start-atなどの中のRegexが間違っていた場合は、ベストエフォートで完全一致でサンプルコードを探しています。

##### 負のoffset

通常はファイルを上から読み込み、処理し、そのまま出力しますが、offsetはマイナスの数字に対応しているため、時には前のN行を出力する必要があります。その機能を実装するために、直近のN行だけをリングバッファに保持しながらストリーミングすることにしました。負のoffsetを指定したマッチに出会った場合は、バッファに溜まった対象の箇所を出力し、バッファをリセットします。

##### インデントの統一

スキップ機能でサンプルコードを複数の箇所から組み立てることができますが、その場合、インデントがずれる可能性があります。そのため、インデントを自動的に合わせる処理を入れています。

##### アトミックな更新

各ファイルは同じディレクトリの一時ファイルへ書き出し、成功した場合のみ `os.Rename` で置き換えます。クラッシュや記述ミスがあっても、書きかけで壊れたドキュメントが残ることはありません。

# コード内のコメントにあるサンプルも同期できる godocsync

https://github.com/sollniss/godocsync

これまでの話はmdファイル内のコードなので、ぶっちゃけ色々なツールはすでにあると思います。求められている機能も色々で、mdsyncより使いやすいツールもあるかもしれません。

ただし、（Goの）コード自体にあるサンプルを同期できるツールは自分が知っている限りまだ存在しませんでした。

ではまずgodocsyncでできることを紹介します。以下のコードが使い方です。

```go
// Greet returns a greeting.
//
// Example:
//
//	Greet("world")
func Greet(name string) string {
  return "Hello, " + name + "!"
}

func _() {
  // #example Greet
  Greet("world") // Hello World!
  // #endexample
}
```

Goのドキュメントのコメントの中で、タブ（または半角スペース1つ＋タブ）のあとに書くコメントはコードとしてみなされます。対象の関数や型の簡単な使い方を書くことが多いと思います。godocsyncはそれらの箇所をピックアップし、同じ名前の `#example` でマークされたコードを探し、同期します。パッケージレベルのドキュメントのコメントは `#example package` で同期可能です。先ほどのmdsyncの`#region`の考え方を応用しています。

もちろん、複数のコードブロックも対応しています：

```go
// Process does two things.
//
// Parsing:
//
//	Parse(input)
//
// Rendering:
//
//	Render(parsed)
func Process() {}

func _() {
  input := ""
  parsed := result{}

  // #example Process 1
  Parse(input)
  // #endexample

  // #example Process 2
  Render(parsed)
  // #endexample
}
```

スキップも、もちろん、可能です：

```go
setup()
// #example Foo
step1()
// #endexample
cleanup()
// #example Foo
step2()
// #endexample
```

そして、インラインでコードをサンプルとしてピックアップすることもできます：

```go
_ = /* #example MyString */ MyString("hello") /* #endexample */
```

## 特徴

##### godocsync はリンターである

godocsyncは厳密に言いますと、リンターです。なので、コードサンプルがずれているよという警告を出すことができ、`-fix`フラグを加えると、修正もできます。

```
godocsync ./...
godocsync -fix ./...
```

そのため、サンプルは必ず、パッケージ内、もしくは`_test`パッケージにないと、ツールが認識できません。

実は、Goのリンターにちょっと詳しい人はこの時点で「ん？」になるかもしれません。なぜかというと、Goのリンターは必ずモジュラーで、パッケージ単体でコードを処理します。そして、パッケージを処理する際に、基本的にそのパッケージの中身しか見れません。少し工夫すればインポートされたパッケージも見れますが、インポートしていないパッケージは基本見れません。これは、インポートの関係性がないパッケージは同時に処理されるからです。パッケージ`a`が パッケージ`b`をインポートしている場合のみに、`b`を先に処理しないと、`a`の処理ができないのですが、`a`と`b`と全く関係のないパッケージ`c`は`b`と同時に処理すれば、速く終わりますね。

そう考えると `a_test` は基本的に `a` をインポートしているため、リンターが `a` を先に処理してしまいます。`a`に古くなったコードサンプルが入っているとして、それをどのように`a_test`にある`#example`を比較したら良いかというと、インポートですね。`a_test`から`a`を遡ってサンプルコードがマッチしているかどうかを計算できますが、ここで仕様の問題がわかりました。

Goのリンターには、現在処理中のパッケージの警告しか出せない、という仕様がありました。つまり、`a_test`を処理している際は、`a_test`の警告は出せますが、`a`の警告は出せません。`a`はすでに処理済みですね。

ここで少しチートしました。
```go
pass.ReadFile = os.ReadFile
```

こうすることでパッケージ外のファイルも自由にアクセスでき、警告も出せます。つまり、godocsyncは完全にリンターなのですが、リンターのルールを少し破っているため、他のリンターとの組み合わせはあまりおすすめしません（レースが発生するリスクがあると思います）。

## こだわった点

まずはリンターとして実装している時点ですでにかなりこだわっていますが、コードのずれを検知できるのは大きなメリットだと思います。最初はmdsyncと同じようにドキュメンテーションコメントにマーカーを入れることでできないかと試していましたが、コメントはプレーンテキストとして読まれることが多いので、どうも残ってしまいますね。リンターを使うことで検知も同期自体も簡単にできることに気づき、そっちにしてみました。

リンターだからこそのメリットとしては、サンプルコードはただの文字列ではなく、ASTとして存在しているため、スキップなどがあっても`go fmt`が内部で利用しているコード（`go/format`パッケージ）をそのまま使って、分散されたサンプルコードをピックアップしたあとに一度きれいにフォーマットしてからドキュメンテーションのコメントに反映することができます。
